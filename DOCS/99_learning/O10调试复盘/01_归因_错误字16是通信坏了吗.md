# 归因 ①：错误字全是 16，是主控板通信坏了吗？

> **结论：❌ 被否定。** 左手通信链路一直正常，"通信异常"是个吓人的名字，但链路根本没断。

## 1. 观测（看到了什么）

- 左手执行 arm（上电使能）失败，系统返回：`fault is latched`（故障已锁存）。
- 查看错误报告，错误字是一串 `[16, 16, 16, ...]`。
- 16 的二进制是 `0001 0000`，也就是第 4 位（bit4）置位，名字叫 **commu_except（通信异常）**。

```
错误字 = 16 = 0b00010000
                   ^
                  bit4 = commu_except（通信异常）
```

## 2. 推测（猜了什么 · 为什么这么猜）

**猜测：左手主控板的通信坏了。**

理由很"合理"：系统明明白白标着"通信异常"，还因为这个标记把故障锁存了，不许继续控制。就像车仪表盘亮"发动机故障灯"，第一反应当然是"发动机坏了"。

## 3. 验证（怎么证明这个猜测）

不改任何东西，直接问硬件本人：

1. 改用**单关节逐个读取**（`get_error_report(j)`，j=1..10），不依赖批量接口。
2. 同时读位置、温度、电流这些物理量。
3. 顺带查了一下日志里刷屏的 `query_errors returned 0 reports` 是**哪一侧**在刷。

## 4. 结果（验证怎么说）

- ❌ **位置、温度、电流全部正常可读**——通信链路是通的。一个通信"坏掉"的手，不可能把位置温度电流都报出来。
- ❌ 刷屏的 `query_errors returned 0 reports` 是 **RIGHT（右手）侧**在刷——**右手根本没接**，跟左手毫无关系。

## 5. 结论与教训

**"commu_except" 这个名字吓人，但左手通信根本没坏。** 真正的问题在别处。

> 教训①：**不要被"像故障的名字"吓住**。先验证"链路是否真的断了"，再下结论。名字只是标签，证据才是真相。
