# 归因 ⑤：手不动，是 SDK 配置/签名传错了吗？

> **结论：❌ 被否定。** SDK 用"拒绝 0 号设备"的报错方式证明了当前配置（hand_device_id=1）是正确的。

## 1. 观测（看到了什么）

- arm 已经成功（`motion_enabled=True`），但往 `/o10_control/left/command` 发目标位置，**手纹丝不动**。
- 这时候注意到一个疑点：SDK 的 pyi 接口文档写的是 `create_hand_by_hcan(product_type, ...)`，跟实际用法对不上。

## 2. 推测（猜了什么 · 为什么这么猜）

**猜测：SDK 配置或函数签名传错了，导致命令根本没发到硬件。**

理由：文档签名和实际签名不一致，很可疑；配置里 `hand_device_id` 之类的参数也值得怀疑。

## 3. 验证（怎么证明这个猜测）

- 直接改参数做**反向实验**：把 `hand_device_id` 从 1 改成 0 再初始化。
- 看 SDK 的反应。

## 4. 结果（验证怎么说）

- ❌ SDK 当场抛异常拒绝：
  ```
  ValueError: hand_device_id must be an explicit integer in 1..255
  ```
- ❌ 这个报错恰恰**反证**了：SDK 对参数有明确校验，`0` 被拒、`1` 合法——**当前配置 1 就是对的**，配置没问题。

```
hand_device_id=0  → SDK 报错拒绝（0 非法）
hand_device_id=1  → SDK 接受（当前配置）  ← 配置正确
```

## 5. 结论与教训

**配置没传错，别急着改参数。**

> 教训⑤：**"报错方式"本身就是证据。** 一个会严格校验参数的 SDK，比一个默默吞掉错误参数的 SDK 好排查得多——它帮你排除了配置这条线。
