# 归因 ③：commu_except 是致命硬件故障，锁存是"负责任"的？

> **结论：❌ 被否定。** 官方 SDK 源码明确：commu_except 是**历史通信错误标记**，正常、不阻止控制。系统拿它锁存故障是"加工逻辑错了"。

## 1. 观测（看到了什么）

- 真实情况：只有零星关节带 16（bit4 commu_except）。
- 但系统只要看到错误字非零（含 bit4），就把故障锁存，拒绝 arm。

```
系统现在的逻辑：
  错误字 & 任何错误位 != 0  ──▶ 锁存故障，拒绝控制
  于是 bit4 一出现，手就"被锁死"
```

## 2. 推测（猜了什么 · 为什么这么猜）

**猜测：commu_except 是致命硬件故障，系统锁存是"负责任"的。**

理由：它名字带 "except（异常）"，又是"通信"层面的，像硬件坏了；系统宁可不动作也不乱动，看起来很安全。

## 3. 验证（怎么证明这个猜测）

不猜了，直接去翻**官方 SDK 源码**（权威定义）：

- 官方测试 `test_omnihand_2025.py` 第 327-328 行，白纸黑字：
  **commu_except 是"历史通信错误"标记，正常现象，且不阻止控制。**
- 官方 demo（`demo/omnihand_2025/`）**从来不查错误报告**，直接下发控制命令。

```
官方源码（327-328 行）大意：
  commu_except = 历史通信错误（正常，不影响控制）
官方 demo：不检查错误报告，直接控制手
```

## 4. 结果（验证怎么说）

- ❌ **不是致命故障**。官方把它定义为"历史通信标记"——就像手机偶尔显示"上次通话有信号波动"，不代表现在打不了电话。
- ❌ 系统锁存行为**不合理**：拿着一个官方说"正常、不阻止控制"的标记，把整只手锁死。

## 5. 结论与教训

**硬件没坏，工具读数也正常，坏的是"加工逻辑"：系统把"历史标记"当成了"致命故障"。**

> 教训③：**字段语义以官方源码/权威定义为准，不按名字猜。** "异常"两个字在硬件行业里经常只是"记录一下"，不代表"坏了"。
