# 归因 ⑦：feedback_ready 永远 false，是 control 的反馈逻辑写错了？

> **结论：❌ 被否定。** control 逻辑没错——是 provider **压根从不发布** joint_states（架构缺口）。先确认"对方有没有能力"，再怀疑"自己逻辑错"。

## 1. 观测（看到了什么）

- 手已经能动了，但控制会话一直等不到反馈就绪：`feedback_ready=False`。
- control 里有一大段"反馈是否就绪"的判断逻辑，看起来嫌疑很大。

## 2. 推测（猜了什么 · 为什么这么猜）

**猜测：control 的反馈判断逻辑写错了，导致永远判不就绪。**

理由：feedback_ready 是 control 算出来的，它 false，当然是它的问题。

## 3. 验证（怎么证明这个猜测）

- 不急着改 control，先问一个更基础的问题：**provider 到底有没有在发布 joint_states？**
- 查 provider 的发布者列表 / 订阅统计。

## 4. 结果（验证怎么说）

- ❌ **provider 从不发布 joint_states**——这个主题上根本没有任何消息在流动。
- ❌ control 再聪明，也等不到**根本不存在**的消息。

```
control 在等：/o10/left/joint_states ←（空，永远没人发）
provider 在干嘛：只收命令、报错误，从不发反馈 ← 架构缺口
```

- 补充：这个缺口**文档里早就预告过**（架构文档写明 provider 尚未实现周期反馈），只是今天第一次在真机上暴露。

## 5. 结论与教训

**先确认"对方有没有能力"，再怀疑"自己逻辑错"。** 一个从不发布消息的节点，不可能被"正确的判断逻辑"等到。

> 教训⑦：排查"等不到数据"类问题时，第一步永远是**确认数据源头是否在产生数据**，而不是分析等待方的逻辑。
