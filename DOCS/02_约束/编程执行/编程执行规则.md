# 编程执行规则

本文件合并旧约束中的上下文加载、从零开发、已有实现改造、接口对齐、TDD、Debug、文件存放、Git 安全和 Skill 加载规则。适用于编码、测试、行为变更、故障修复及 Git 操作。

## 1. 先识别任务类型

开始前先判断任务属于哪一种：

| 类型 | 判断信号 | 首要动作 |
| --- | --- | --- |
| 新建能力 | 仓库中不存在对应程序、模块或入口 | 澄清需求并形成最小蓝图 |
| 修改已有能力 | 已有代码上做适配、加固、重构或补测试 | 先盘点 AS-IS，再定义 TO-BE 与 Delta |
| Debug / Bugfix | 报错、失败、行为不符、数据异常或性能回归 | 先建立可重复的失败信号 |
| 普通维护 | 小幅代码、配置或测试调整 | 确认范围后做最小修改 |
| Git | 状态、提交、同步、分支、合并或远端操作 | 先检查仓库状态和写操作授权 |

任务类型不清且不同解释会明显改变实现时，列出差异并请求确认；不得静默选择更大的范围。

## 2. 上下文加载顺序

1. 读取根 `AGENTS.md`。
2. 读取 `DOCS/02_约束/用户概念体系/用户概念与术语规则.md`，使用统一术语。
3. 定位阶段，读取相关 `DOCS/01_知识/`、对应 `src/<stage>/README.md` 和必要的工程状态。
4. 读取当前任务直接依赖的接口、代码、测试和最近有效记录；不全库扫读历史日志。
5. 读取 `skills/INDEX.md`；命中触发条件时完整读取对应 Skill。
6. 开始修改前检查工作区、允许写入范围和验证入口。

默认不读取 `DOCS/98_archive/`、`DOCS/99_learning/`、大型外部资料或历史执行日志全文。只有当前问题需要具体历史证据时才定点读取，并区分历史参考与当前权威。

## 3. 实现前必须明确的七项信息

无论新建还是修改，至少明确：

1. 功能目标：解决什么问题。
2. 输入输出：文件、参数、对象、日志或外部接口分别是什么。
3. 运行环境：在哪个阶段、进程和依赖环境中运行。
4. 依赖关系：直接调用谁、被谁消费、等待谁完成。
5. 数据流：数据从哪里来，经过什么边界，到哪里去。
6. 边界与失败：明确不做什么，异常和缺失如何表现。
7. 成功标准：运行什么检查、观察到什么才算完成。

目标、直接依赖、允许修改范围或验收方式缺失且无法从仓库确认时，停止实现并报告缺口。

## 4. 新建能力的蓝图

从零创建程序或模块前，先形成足以指导实现的最小蓝图：

- 名称、阶段归属和预期文件落点。
- 单一职责与明确不负责内容。
- 输入输出和依赖。
- 对外接口及失败语义。
- 最小目录变化。
- 测试 seam、验证命令和可观察结果。

只为当前已确认能力设计，不提前创建未来扩展、空包、共享框架、未使用配置或第三方依赖。

## 5. 修改已有能力：AS-IS → TO-BE → Delta

修改现有代码前必须先盘点：

- 相关文件、入口、类、函数、配置和已有测试。
- 当前真实输入输出、内部约定、失败语义和可观察信息。
- 已经稳定且必须保留的行为。
- 当前行为与目标行为的差距和已知风险。

`AS-IS` 必须来自实际代码、配置、测试或可复现运行，不得把已有能力描述成待实现空白。`TO-BE` 必须写成可验收承诺，不是愿望清单。每个 `Delta` 至少说明：变更对象、当前行为、目标行为、影响范围、兼容性、实现方式、验收方式和回滚方式。

默认保护原始可运行路径。能通过小接口或 adapter 隔离变化时，优先保持核心逻辑稳定；破坏性修改必须获得明确授权并说明回滚方法。

## 6. 直接上游接口对齐

消费上游数据、文件、类型、状态、配置、函数或运行顺序前，必须回答：

```text
当前能力直接依赖谁？
从上游消费什么接口或产物？
上游实际输出与当前期望是否一致？
若不一致，修改当前能力、先定义上游接口，还是暂停确认？
```

不得在下游重新定义字段相似但语义不同的对象，不得偷偷兼容多个猜测版本，也不得为了让当前测试通过而越权修改上游。接口未稳定时，将其记录为未知或先做接口对齐；验收至少覆盖一个真实的上游兼容点。

## 7. 实现范围与修改纪律

- 只实现当前目标要求的最小能力。
- 只修改能够追溯到目标的文件和行，匹配现有风格。
- 不顺手重构、格式化或清理无关代码。
- 不添加验收标准未覆盖的配置和未来扩展。
- 清理由本次改动制造的未使用对象，但不擅自清理既有死代码。
- 发现范围外问题时记录证据和建议，不把它混入当前修改。
- 修改上下游两侧、共享文件或第三方代码必须在任务范围中被明确授权。

## 8. TDD 与验证闭环

涉及新增行为、行为变更或 bug 修复时，按垂直切片推进：

1. 为一个可观察行为写测试或最小复现。
2. 运行并确认它因目标问题失败；无法运行时说明具体环境缺口。
3. 写最少实现使该行为通过。
4. 运行对应检查。
5. 只在 green 后做必要整理。
6. 再进入下一个行为。

测试通过公共接口或约定 seam 验证行为，不绕过接口测试内部细节。不得先堆积大量测试再一次性实现，也不得用 TDD 扩大任务范围。

将模糊任务转成可观察目标：

- “添加校验”＝无效输入测试 + 明确错误行为。
- “修复 bug”＝先复现 + 修复后同一信号转绿。
- “重构”＝变更前后外部行为一致。
- “新增字段”＝输出样例或断言能够观察字段及语义。

## 9. Debug / Bugfix

Debug 先建立稳定的 pass/fail 信号，再提出和排除假设。依次确认复现入口、输入样例、涉及阶段、日志/错误、最近变化和直接依赖；不要把环境失败当成业务 bug 修。

修复后必须说明：

- 原始现象和复现方式。
- 根因证据，而非仅描述修改位置。
- 修改范围和为何足够。
- 回归测试或最小复现如何从失败变为通过。
- 未验证项、环境阻断和剩余风险。

## 10. 验证阶梯与高风险执行

优先在最低风险层级证明行为，再逐级扩大：

```text
静态检查 / 单元测试
→ import / config / codec / mock
→ dry-run / fake input
→ 离线真实数据或真实模型
→ shadow-run
→ 真实硬件 smoke test
```

能在本地执行的层级必须实际执行。缺少模型、SDK、ROS 环境或硬件时，记录为环境阻断或硬件阻断，不能写成通过，也不能伪造日志。

真实硬件相关变更必须提供不触发真实动作的验证路径、安全前置条件、人工观察点、失败停止条件和回滚方式。高风险发送链路不得与无关的大型重构混在一次修改中。

## 11. 验收证据

验收不能只写“测试通过”，至少记录：

- 工作目录、命令和必要环境。
- 测试输入或 fixture。
- 观察点：stdout、日志、返回值、生成文件、shape、状态或现场行为。
- 明确的通过现象与失败现象。
- 已验证项、未验证项及原因。
- 对应的排查入口和必要回滚方式。

局部测试只证明本次修改的局部行为；跨模块或阶段成果还需要对应接口/集成检查。需要人工或真机验收时，自动化结果不能替代人工确认。

## 12. 文件落点与生成物隔离

| 内容 | 当前落点原则 | Git |
| --- | --- | --- |
| 可维护源码 | 对应 `src/<stage>/` | 进入 |
| 可维护测试 | 对应阶段的测试目录，建立时同步阶段 README | 进入 |
| 配置模板、依赖清单 | 对应阶段的配置或源码目录 | 进入 |
| 原始 MCAP | 仓库外或被忽略的数据目录，只读 | 不进入 |
| 数据集、中间数据、报告实例 | 被忽略的 artifacts/datasets/runs 目录 | 不进入 |
| 模型、checkpoint、ACT bundle | 被忽略的 models/artifacts 目录 | 不进入 |
| 运行日志、配置快照、缓存、测试输出 | 被忽略的 runs/logs/cache 目录 | 不进入 |
| 虚拟环境、ROS 构建产物 | 本地环境及 build/install/log 目录 | 不进入 |
| 外部 SDK 源码 | 未建立 vendor 策略前不复制进仓库 | 不进入 |

不得覆盖 `raw MCAP`，不得把生成物散落到仓库根目录或源码目录。测试代码应进入 Git，测试运行输出不进入。具体阶段落点只有在真实实现需要时才建立，不为空结构提前建目录。

## 13. Git 安全

### 授权与检查

- 只有用户明确要求，或当前任务明确授权，才执行提交、推送、拉取、建/切分支、合并或删除。
- 写操作前检查 `git status --short --branch`、当前分支、远端和待操作范围。
- 保留非本任务变更；暂存时使用明确路径，不使用覆盖范围不明的批量操作。
- 提交前检查嵌套仓库、超大文件、缓存、密钥、私有配置、模型和数据产物。

### 同步与阻断

- 拉取默认使用 fast-forward only。
- 遇到远端领先、本地分叉、冲突、非预期工作区变更或需改写历史时停止并报告。
- 禁止 force push、自动 rebase、自动 amend 或未经确认删除分支。
- 测试或验收未达到明确通过条件时，不把变更描述为可合并。

旧仓库的长期分支和阶段分支模型不迁入 Dexhit。需要分支策略时根据当前仓库真实协作方式另行定义。

## 14. Skill 唯一权威与加载

`skills/` 是 Skill 唯一实体目录。`.agents/skills` 和 `.claude/skills` 只能是指向 `../skills` 的相对符号链接，不得维护副本。

使用流程：

1. 先读 `skills/INDEX.md` 的用途和触发条件。
2. 只在任务匹配时完整读取对应 `SKILL.md`。
3. Skill 引用的必要模板或规则按其说明读取，不递归加载无关资料。
4. 新增、移动、删除或改变触发条件时同步更新索引。

Skill 不得覆盖用户明确范围、本文件的 Git 安全和生成物隔离规则。

## 15. 完成交接

完成后至少说明：目标和未做范围、实际修改文件、关键行为变化、测试或复现过程、运行命令、验证结论、未验证项与剩余风险。文档、索引或工程状态确实受影响时同步更新对应权威入口；不得为一次小改动制造重复执行日志。
