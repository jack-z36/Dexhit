# 用户概念与术语规则

本文件维护用户已经确认的名称、概念边界和表达口径。它约束“如何理解和表达项目”，不替代 `DOCS/01_知识/` 中的项目事实，也不记录一次性工程状态。

## 1. 概念权威顺序

1. 用户在当前任务中明确给出的定义和修正。
2. 本文件已经登记的稳定术语。
3. `DOCS/01_知识/` 中与术语一致的项目事实。
4. 从代码、旧文档或历史记录推断出的含义。

用户定义与现有文档或代码冲突时，必须显式指出冲突并确认要更新哪一侧；不得静默用 Agent 熟悉的同义词替换用户用语。推断必须标注为推断，不能写成已确认事实。

## 2. 四阶段统一名称

| 旧资料称谓 | Dexhit 代码名 | Dexhit 中文名 | 阶段交付边界 |
| --- | --- | --- | --- |
| 阶段一：数据采集 | `collection` | 数据采集 | `raw MCAP` |
| 阶段二：数据清洗 | `processing` | 数据处理 | `LeRobotDataset v3` |
| 阶段三：模型训练 | `training` | 模型训练 | `ACT bundle` |
| 阶段四：模型部署 | `deployment` | 模型部署 | 现场执行与运行记录 |

当前文档和新代码统一使用 Dexhit 名称。旧称谓只允许出现在迁移审计或历史说明中，不能继续充当目录名、模块名或当前任务类型。

主链固定写作：

```text
collection → raw MCAP → processing → LeRobotDataset v3 → training → ACT bundle → deployment
```

## 3. 核心概念

**阶段（stage）**：主链中具有明确输入、职责和输出的稳定处理区间。阶段不是任务优先级，也不是旧任务层级。

**模块（module）**：阶段内部具有清晰职责和接口的实现单元。模块名称在真实代码边界出现后再确定，不预先为空目录命名。

**产物（artifact）**：一次运行或一个阶段生成、可被验证或交给下游消费的结果。阶段交付产物与缓存、日志等内部生成物必须区分。

**接口（interface）**：下游使用模块时必须知道的全部承诺，包括输入输出、单位、顺序、错误、配置和性能约束；不能只写函数签名。

**契约（contract）**：可用于实现和验收的接口行为说明。已有行为称 `AS-IS`，目标承诺称 `TO-BE`，两者之间的可追踪变化称 `Delta`。

**生成物（generated output）**：数据集、模型、缓存、日志、运行快照、构建目录等由工具或运行过程产生的文件；默认不属于源码。

## 4. 概念定义最低信息

新增或修改一个项目概念时，至少回答：

- 规范名称和应避免的同义词。
- 它是什么，以及明确不是什么。
- 它位于哪一阶段或边界。
- 它的上游来源和下游消费者。
- 若它是数据或状态：字段、取值、单位、坐标系、有效性和缺失语义。
- 当前是已确认事实、目标设计、未知问题还是历史参考。

同一概念只保留一个当前权威定义。聚合文档可以引用它，但不得复制出另一份可独立维护的定义。

## 5. 产物词汇

- `raw MCAP`：collection 的原始记录边界。不得简称为含义不清的“原始包”，也不得被下游覆盖。
- `LeRobotDataset v3`：processing 面向 training 的规范数据集交付。没有确认格式时，不用“清洗后数据”冒充该交付已经成立。
- `ACT bundle`：training 面向 deployment 的完整模型交付。它不等同于单个权重文件；bundle 组成尚未定义时必须标记为未知。
- “主链”：只指本文件第 2 节的完整链路，不泛指任意程序调用链。

## 6. 状态与不确定性表达

文档必须区分以下四种口径：

- **当前事实**：代码、数据或已经验收的行为能够证明。
- **目标设计**：计划实现但尚未验证的 TO-BE 行为。
- **未知问题**：信息不足，不能由现有资料推出。
- **历史参考**：只用于解释来源，不是当前权威。

不得把“计划”“应当”“可能”写成“当前已经”；不得把环境缺失或硬件缺失下未执行的验证写成通过。

## 7. 已退出当前语言的旧概念

旧资料中的任务层级、循环调度、固定机器分工、旧阶段分支、场景编号和旧硬件包名称不进入 Dexhit 第一版通用语言。若未来确实需要其中某个概念，应根据 Dexhit 的实际工作重新定义，而不是恢复旧含义。

## 8. 表达偏好

- 说明文字以中文为主，代码标识、文件名、格式名和命令保持原文。
- 路径统一写仓库相对路径；不写开发者机器绝对路径。
- 优先使用具体输入、输出、观察点和通过现象，避免“处理一下”“支持功能”“正常运行”等不可验收表述。
- 不引入未确认的传感器、消息 schema、硬件、依赖或运行命令。
