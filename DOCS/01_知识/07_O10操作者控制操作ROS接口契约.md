# O10 操作者控制操作 ROS 接口契约

本文固定 Phase 1 操作者对 O10 控制节点发起状态转换的 ROS 接口。接口形态、逐侧身份、通用应答以及 `arm`、`disarm`、`clear_fault` 的完整语义均已固定。

## 为什么使用 Service

`arm`、`disarm` 和 `clear_fault` 都是一次明确的状态转换请求。操作者必须知道请求是否真正完成，并在失败时得到稳定的机器可读原因，因此使用一次“请求—应答”的 ROS Service。

- 不使用 Topic：Topic 适合单向事件流，不能自然表达某一次请求是否被接受；
- 不使用 Action：Action 适合长时间运行、需要进度与取消的任务，这三个操作不需要持续反馈；
- 不通过写入 `O10ControlState` 操作控制：状态消息是只读观测，不能成为控制输入。

## Service 名称

左右手拥有完全独立的六个 Service：

```text
/o10_control/left/arm
/o10_control/left/disarm
/o10_control/left/clear_fault

/o10_control/right/arm
/o10_control/right/disarm
/o10_control/right/clear_fault
```

手侧由 Service 名称唯一确定，请求中不重复携带 `side`。一侧操作不得修改另一侧的 `armed`、故障或硬限制器状态。

## 共用 Service 类型

三个操作共用：

```text
rokoko_omnihand_msgs/srv/ControlOperation
```

定义为：

```ros
# Request is empty. The service name identifies the operation and side.
---
bool success
uint8 result_code
string message
rokoko_omnihand_msgs/O10ControlState state
```

请求为空的原因是：操作种类已经由 `arm`、`disarm` 或 `clear_fault` 的 Service 名称确定，手侧也已由 `left` 或 `right` 确定。禁止再增加含义重复、可能与 Service 名称冲突的 `operation` 或 `side` 请求字段。

## 通用应答语义

`success` 表示该次请求要求的状态在 Service 应答产生前已经成立：

- `arm` 成功：同侧 `armed=true`；
- `disarm` 成功：同侧 `armed=false`；
- `clear_fault` 真正执行并成功：同侧锁存故障已清除，且 `armed=false`；若请求到达时本来就无锁存故障，则按后文幂等规则返回且不改变现有授权。

`success=false` 表示本次请求没有完成所要求的状态转换。失败请求不得排队、缓存或在前置条件以后成立时自动重放。

`result_code` 是供程序稳定判断结果的枚举值。它的含义由具体操作分别定义，调用方不得依赖 `message` 文本作状态机判断。

`message` 是给操作者阅读的说明，可以本地化或调整措辞，不构成机器接口兼容性承诺。

`state` 是该请求处理完成后、在同一控制状态锁保护下生成的同侧 `O10ControlState` 快照。它必须满足：

```text
state.event == EVENT_OPERATOR_REQUEST
state.side == Service 名称中的手侧
```

该快照用于让调用方立即理解结果；控制节点还必须在对应 `/o10_control/{side}/state` Topic 发布同一操作事件。Service 应答中的状态和 Topic 状态都是观测结果，不反向驱动控制。

## 原子性与并发

每侧对操作请求、目标处理、反馈处理、错误状态处理和超时事件进行串行化或等价的原子状态更新。Service 不得返回一份由多个时刻拼接而成的状态。

如果左右两侧同时收到请求，两侧可以并行处理，但必须使用各自独立的状态。若同一侧多个操作近乎同时到达，按照控制节点实际取得该侧状态锁的顺序逐个执行，每个应答均反映它完成后的状态。

`arm` 成功本身不发布硬件位置命令；它只改变操作者授权。必须等下一条新鲜、合法的软目标到达后，控制节点才可以依据 `motion_enabled` 和硬限速契约发送命令。

`disarm` 只停止后续新命令，不自动张手、回零、追赶旧目标或执行硬件急停。`clear_fault` 也不自动重新使能；成功后必须由操作者另行调用 `arm`。

## arm 操作

`arm` 的含义是允许该侧在随后收到新鲜、合法软目标时产生硬件命令。调用成功本身不发布位置命令，也不重置硬限速器。

### 原子成功条件

处理请求的同一个原子状态更新中，必须满足：

\[
\boxed{
\operatorname{armAllowed}_s
=
\operatorname{feedbackReady}_s
\land \operatorname{errorMonitorReady}_s
\land \operatorname{targetReady}_s
\land \operatorname{targetFresh}_s
\land \neg\operatorname{faultLatched}_s
}
\]

- `feedback_ready`：已读取新鲜、合法的真实主动关节位置并初始化硬限速器；
- `error_monitor_ready`：已获得当前有效的硬件错误状态，且错误轮询未超时；
- `target_ready`：本次控制进程中至少收到并验证过一条合法的 10 维软目标；
- `target_fresh`：最近合法目标的上游输入年龄和本机接收间隔均未超时；
- `fault_latched=false`：不存在尚未人工清除的锁存故障。

前置条件检查和 `armed=true` 写入必须由同一侧状态锁串行化，不能在检查后释放状态锁再写入。失败请求不改变 `armed`，也不排队。

### arm 结果码

`ControlOperation` 为 `arm` Service 定义：

```ros
uint8 ARM_SUCCESS=0
uint8 ARM_ALREADY_ARMED=1

uint8 ARM_REJECTED_FAULT_LATCHED=10
uint8 ARM_REJECTED_FEEDBACK_NOT_READY=11
uint8 ARM_REJECTED_ERROR_MONITOR_NOT_READY=12
uint8 ARM_REJECTED_TARGET_NOT_READY=13
uint8 ARM_REJECTED_TARGET_STALE=14
uint8 ARM_REJECTED_CONTROL_STATE=15
```

首次满足全部条件并完成授权时：

```text
success = true
result_code = ARM_SUCCESS
state.armed = true
```

若请求到达前已经 `armed=true`，则操作幂等成功：

```text
success = true
result_code = ARM_ALREADY_ARMED
state.armed = true
```

重复 `arm` 不发送命令、不重置硬限速器、不刷新目标时间，也不改变最后已发送命令基准。

### 多条件失败优先级

如果多个条件同时失败，`result_code` 只报告以下顺序中优先级最高的一项：

```text
ARM_REJECTED_CONTROL_STATE
→ ARM_REJECTED_FAULT_LATCHED
→ ARM_REJECTED_FEEDBACK_NOT_READY
→ ARM_REJECTED_ERROR_MONITOR_NOT_READY
→ ARM_REJECTED_TARGET_NOT_READY
→ ARM_REJECTED_TARGET_STALE
```

完整条件必须通过同一应答中的 `O10ControlState` 读取。例如反馈和错误监控都未就绪时，主结果为 `ARM_REJECTED_FEEDBACK_NOT_READY`，状态快照仍同时表达两个 false。任何拒绝均返回：

```text
success = false
state.armed = false
```

## disarm 操作

`disarm` 的唯一授权状态转换是：

\[
\boxed{
\operatorname{armed}_s\leftarrow\mathrm{false}
}
\]

该状态转换与同侧目标处理必须串行化。从转换完成开始，不得再由后续软目标发布新的硬件位置命令；转换前已经发送给硬件的命令无法撤回。

### 可调用条件与副作用边界

`disarm` 不要求反馈、错误监控、软目标或设备处于就绪状态。普通硬件故障不能阻止撤销授权。它只对本侧执行以下操作：

- 将 `armed` 置为 false；
- 立即使派生的 `motion_enabled` 为 false；
- 停止处理完成后的新硬件位置命令；
- 保留锁存故障及其原因，不执行故障清除；
- 保留软目标历史和最近目标观测；
- 不自动张手、回零、断开驱动或发送额外的“停止位置命令”。

另一侧不受影响。

### disarm 结果码

`ControlOperation` 为 `disarm` Service 定义：

```ros
uint8 DISARM_SUCCESS=20
uint8 DISARM_ALREADY_DISARMED=21
uint8 DISARM_REJECTED_CONTROL_STATE=22
```

若请求前 `armed=true`，并成功将其置为 false：

```text
success = true
result_code = DISARM_SUCCESS
state.armed = false
state.motion_enabled = false
```

若请求前已经 `armed=false`，则幂等成功：

```text
success = true
result_code = DISARM_ALREADY_DISARMED
state.armed = false
state.motion_enabled = false
```

重复 `disarm` 不发送硬件命令，也不改变故障状态。`DISARM_REJECTED_CONTROL_STATE` 仅用于控制节点内部状态矛盾、无法保证本侧原子更新的严重情况；返回时控制节点必须按安全不变量故障处理，不能因为 Service 失败而继续发送命令。

### 硬限速器状态

成功 `disarm` 后保留最后实际发送的位置基准：

\[
\mathbf q_s^{\mathrm{base}}
=
\mathbf q_s^{\mathrm{last\_sent}}.
\]

同时丢弃此前累计的时间额度，并停止累计解除授权期间的时间。下一次 `arm` 成功时重新建立本机单调时钟起点，但不修改上述位置基准。因此解除授权持续多久都不能增加下一条命令允许的关节变化量。

该基准仅在硬件状态仍可信时保留。如果 `disarm` 期间发生设备断连、重启、非法反馈或其他使真实位置不再可信的事件，控制节点必须进入锁存故障，使 `feedback_ready=false`，并在清除故障时重新读取真实位置；此时禁止继续使用旧基准。

## clear_fault 操作

`clear_fault` 只清除控制节点内部的逐侧锁存故障，不是厂商硬件故障复位命令。若 O10 仍报告过热、过流、堵转、电机异常或通信异常，操作必须失败，不能用软件强行把真实硬件错误标记为正常。

### 同步执行流程

若请求到达时 `fault_latched=true`，控制节点在有限的配置超时内同步执行以下步骤：

1. 原子设置 `armed=false`，禁止产生新硬件位置命令；
2. 通过硬件 Adapter 主动查询一份新的 O10 错误状态；
3. 验证错误状态身份、维数和格式，并确认 10 个主动关节的**致命错误位**（bit0–bit3）全部为零；`commu_except`（bit4，厂商历史通信标记）不阻止清除；
4. 确认 Adapter、设备连接和通信当前健康；
5. 在不先改变手姿态的前提下，独立读取一份新的真实 10 维主动关节位置；
6. 验证手侧、维数、固定顺序、有限值和该侧关节限位；
7. 丢弃旧位置基准和旧时间额度，用本次真实位置重新初始化硬限速器；
8. 原子清除锁存故障，保持 `armed=false`。

成功后的状态满足：

\[
\boxed{
\begin{aligned}
\operatorname{faultLatched}_s&=\mathrm{false},\\
\operatorname{armed}_s&=\mathrm{false},\\
\operatorname{feedbackReady}_s&=\mathrm{true},\\
\operatorname{errorMonitorReady}_s&=\mathrm{true},\\
\mathbf q_s^{\mathrm{base}}&=\mathbf q_s^{\mathrm{measured}}.
\end{aligned}
}
\]

其中 \(\mathbf q_s^{\mathrm{measured}}\) 是本次请求期间独立读取的真实主动关节位置，\(\mathbf q_s^{\mathrm{base}}\) 是硬限速器下一次运动使用的位置基准。清除成功不自动调用 `arm`，操作者必须另行请求授权。

### 失败语义

步骤 1 一旦执行，即使后续步骤失败也保持 `armed=false`。步骤 2 至步骤 7 任一步失败时：

\[
\boxed{
\operatorname{faultLatched}_s=\mathrm{true},
\qquad
\operatorname{armed}_s=\mathrm{false}
}
\]

同时不得发送位置命令、不得恢复旧硬限速器基准、不得部分清除故障、不得自动重试或排队。操作者排除原因后必须再次调用 `clear_fault`。

Service 采用有限超时内的同步请求—应答，不改为 Action。具体查询、读取和总超时数值需要由真机测试标定。

### clear_fault 结果码

`ControlOperation` 为 `clear_fault` Service 定义：

```ros
uint8 CLEAR_FAULT_SUCCESS=30
uint8 CLEAR_FAULT_ALREADY_CLEAR=31

uint8 CLEAR_FAULT_REJECTED_CONTROL_STATE=40
uint8 CLEAR_FAULT_REJECTED_COMMUNICATION_UNHEALTHY=41
uint8 CLEAR_FAULT_REJECTED_ERROR_QUERY_TIMEOUT=42
uint8 CLEAR_FAULT_REJECTED_ERROR_STATUS_INVALID=43
uint8 CLEAR_FAULT_REJECTED_HARDWARE_ERROR_PRESENT=44
uint8 CLEAR_FAULT_REJECTED_FEEDBACK_READ_TIMEOUT=45
uint8 CLEAR_FAULT_REJECTED_FEEDBACK_INVALID=46
uint8 CLEAR_FAULT_REJECTED_LIMITER_INIT_FAILED=47
```

完整执行步骤并成功时：

```text
success = true
result_code = CLEAR_FAULT_SUCCESS
state.fault_latched = false
state.armed = false
state.feedback_ready = true
state.error_monitor_ready = true
```

如果请求到达时已经 `fault_latched=false`，并且控制状态不存在矛盾，则幂等成功：

```text
success = true
result_code = CLEAR_FAULT_ALREADY_CLEAR
state.fault_latched = false
```

幂等分支不重新查询硬件、不重新读取反馈、不重置硬限速器，也不改变当前 `armed`。若控制状态内部矛盾，则不能使用 `ALREADY_CLEAR` 掩盖问题。

### 多条件失败优先级

若一次执行中存在多个失败条件，`result_code` 按以下固定顺序报告最先应处理的一项：

```text
CLEAR_FAULT_REJECTED_CONTROL_STATE
→ CLEAR_FAULT_REJECTED_COMMUNICATION_UNHEALTHY
→ CLEAR_FAULT_REJECTED_ERROR_QUERY_TIMEOUT
→ CLEAR_FAULT_REJECTED_ERROR_STATUS_INVALID
→ CLEAR_FAULT_REJECTED_HARDWARE_ERROR_PRESENT
→ CLEAR_FAULT_REJECTED_FEEDBACK_READ_TIMEOUT
→ CLEAR_FAULT_REJECTED_FEEDBACK_INVALID
→ CLEAR_FAULT_REJECTED_LIMITER_INIT_FAILED
```

应答中的 `O10ControlState` 同时提供当前可观测条件；调用方不得把单一结果码解释为其他条件必然正常。

## 录制边界

Service 请求与应答不作为 Phase 1 必录 MCAP Topic。操作者操作造成的状态变化通过 `/o10_control/{side}/state` 中的 `EVENT_OPERATOR_REQUEST` 记录，因此离线回放可以重建何时处理了操作以及处理后的状态。
