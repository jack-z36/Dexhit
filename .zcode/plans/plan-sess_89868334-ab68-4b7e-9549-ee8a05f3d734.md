# acceptance-testing Skill 优化：人机审核关卡 + 执行审查角色 + Skill 联动

针对三个痛点的改动（全部落在既有文件，新增一个角色文件与一份模板节）：

## 1. 人机交互：两道强制审核关卡

状态机新增三个状态：
- `EXPERIMENT_DESIGNING`：生成实验方案。硬件实验（C 档/真实设备/真实抓包）由编排者中继，与用户多轮共同设计（Experiment Agent 先出草案，只写不执行）；纯软件实验自主生成结构化方案。
- `WAITING_HUMAN_EXPERIMENT_REVIEW`：实验方案必经人类审核（补充实验、复验实验无例外）。批准 = request.md 的 Human Approval 节签署；否决回设计态。
- `WAITING_HUMAN_SOLUTION_REVIEW`：解决方案 + 任务清单呈报用户审核，批准才 EXECUTING。

配套：
- Experiment Agent 纪律强化——request.md 视为已批准方案，无法按原样执行（环境不符、步骤矛盾）即停止返回 BLOCKED，禁止自行变更实验方案。
- Solution Agent 强化——solution.md 必须先写 `Goal Definition`（最终目标，可观测、可判定）与 `Success Evaluation`（如何评估已达成：对应探针点 + 复验实验设计），未写清即被编排者拒收。
- 模板增强：request.md 加 `Rationale`（为什么需要、能区分哪些假设）与 `Human Approval` 节；solution.md 加上述两节 + `Human Approval`。

## 2. 新增第五角色：Execution Reviewer

- EXECUTING 内部流程变为：Execution Agent 施工 → Execution Reviewer 审查 → FAIL 重新派发新执行者（携带审查反馈，遵守"禁止阻断子代理"规则）→ 每 task ≤3 修复轮。
- Reviewer 职责：逐条核对 Acceptance Criteria、验证命令是否真实运行且如实记录、是否越出 Allowed Scope、是否符合 ARCHITECTURE 不变量。
- 输出 `execution/TASK-nnn-review.md`；单一裁决四态（复用 dispatch-tickets reviewer 契约）：PASS / FAIL / BLOCKED_ENV / BLOCKED_HARDWARE_EXPECTED + FAIL 具体修复请求。
- 禁止 Reviewer：修改文件、自行修复、宣称验收 PASS（只裁 task）。
- 模型分配 `[reviewer]`：gpt-5.6-luna / high（agent-models.toml + codex-roles/reviewer.md + check-models 同步校验）。

## 3. Skill 联动（各角色在派发模板中绑定仓库已有 Skills，指示先读再干）

| 角色 | 绑定 |
| --- | --- |
| Analysis | `diagnosing-bugs`（可证伪假设、证据不足必须明说） |
| Solution | `to-tickets`（micro task 结构/验收 checkbox）；涉接口设计加 `codebase-design` |
| Execution | `implement` + `tdd`（单任务纪律、预定 seam red-green） |
| Execution Reviewer | `code-review`（Standards/Spec 双轴方法，范围限本 task） |
| 编排者终局 | `code-review`（整个 run 累计 diff 集成门禁） |
| Experiment | 无直接适配（明确写"无"，不硬凑） |
